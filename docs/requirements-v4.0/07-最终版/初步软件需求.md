## 1. 软件背景

任务01已实现个人记账、分类统计、月度预算、数据导出与备份，形态为 Electron 桌面端 + FastAPI + SQLite，数据本地、单用户。v4.0 在此基础上增加「共享账本」，面向宿舍、社团、旅行、聚餐等多人共同消费场景。

共享账本与个人账本并存：个人账本继续负责个人收支；共享账本只记录成员之间的共同支出、分摊和结清状态。两者数据隔离，统计口径分开。

## 2. 欲解决的问题

1. 共同开销散落在微信群、Excel、截图中，容易漏记、重记；
2. 谁垫付、谁参与、谁该付多少靠记忆和手算，容易出错；
3. 多人互相欠款时转账链路长，结清状态不透明，催款尴尬；
4. 社团经费多人经手，缺少权限控制和操作留痕；
5. 共同开销混入个人账本，导致个人统计和预算失真。

## 3. 软件解决方案

1. 建立账号体系与共享账本，账本成员共同维护流水；
2. 每笔支出记录付款人、参与人、金额和分摊方式，系统自动计算应付与垫付；
3. 系统按成员汇总净余额，生成“谁转给谁、转多少”的结算建议；
4. 付款方标记已转账、收款方确认到账，支持部分结清与争议回退；
5. 通过角色权限、软删除和审计日志保证多人协作可追溯；
6. 个人账本与共享账本数据隔离，共享账本内流水与余额对成员透明；
7. 平台只记录账目与结清状态，不实际转移资金。

## 4. 范围与边界

### 4.1 范围内

账号与登录、个人资料、账本创建、邀请与加入、成员与角色、共同支出、分摊、退款、结算、统计、共享预算、站内提醒、导出与备份、审计日志、账号注销。

### 4.2 范围外

| 不做项 | 原因 |
|---|---|
| 真实支付、自动扣款、代收代付 | 涉及金融资质，课程项目不碰 |
| 微信/支付宝账单自动导入 | 需要外部授权，格式不稳定 |
| OCR 小票识别、语音记账 | 成本高，非核心问题 |
| 区块链存证 | 与问题无关，成本高 |
| 多币种、汇率 | 校园场景以人民币为主 |
| 公开社交、账本广场、聊天 | 偏离记账与结算目标 |
| 短信、邮件、微信服务号推送 | 只做站内提醒，避免外部服务依赖 |
| 离线写入、多端实时协同（CRDT） | 与在线写入约束冲突，本期不做 |
| 社团报销审批、财务记账凭证 | 流程复杂，延后到 v5 |
| 校园卡系统对接 | 无授权渠道，不可行 |
| 账本级自定义分类 | v4.0 沿用系统 8 个默认分类 |
| 多租户、灰度发布、运营后台 | 非课程项目目标 |

## 8. 业务规则与数据约束

### 8.1 金额与精度

- 所有金额以整数“分”存储和计算，展示时保留两位小数；
- 单笔支出金额 >0 且 ≤1,000,000 元；
- 分摊结果每人 >0；Σ分摊 = 支出金额；
- 均分余数按“付款人优先，其余按参与顺序”逐分分配；
- 净额合计必须为 0，否则拒绝结算。

### 8.2 日期与时区

- 统一使用 Asia/Shanghai；
- 支出日期不得晚于今天，不得早于 365 天前；
- 结算、审计时间精确到秒。

### 8.3 邀请与成员

- 邀请码 6 位，排除易混淆字符；7 天有效；可撤销；账本上限 50 人；
- 邀请码尝试 5 次/10 分钟，超过锁定 10 分钟；
- 被移除或退出的成员立即失去访问权，历史记录保留；
- Owner 转让后降为普通成员；Owner 不能直接退出。

### 8.4 结算

- 净额 = 已付 − 应付；
- 采用贪心算法：每次让净欠款最多者向净应收最多者转账，金额取两者绝对值较小者；转账笔数 ≤ 成员数 − 1；
- 支持部分结清；已确认的结清记录不因新增支出而撤销；
- 新增支出后重新计算未结清部分；
- 争议由收款方拒绝，状态回到“待确认”，系统不自动裁决。

### 8.5 退款与删除

- 仅支持整单退款；已结算支出不可退款；
- 退款记录按原分摊比例冲销，原支出锁定；
- 软删除 30 天内可由 Owner/Admin 恢复；到期后彻底删除；
- 已结算支出不可编辑或删除；
- 所有变更写审计日志。

### 8.6 并发与幂等

- 支出、结算记录使用版本号；保存时版本不一致返回冲突提示；
- 客户端提交使用幂等键，避免网络重试产生重复记录；
- 同一账本的关键操作按账本维度串行校验。

## 9. 可行性及潜在风险

| 类别 | 结论 | 说明 |
|---|---|---|
| 技术 | 可行 | 账号、权限、分摊、贪心结算均可用现有技术栈实现；实时协同、校园卡、OCR 等已排除 |
| 设备 | 可行 | 现有开发机 + 一台可访问服务器；无需额外硬件 |
| 进度 | 基本可行 | 6–8 周、3 人；需按 P0 优先，P1 可裁剪 |
| 成本 | 可行 | 无付费 API；服务器可用课程或低配云主机 |
| 商业 | 不适用 | 课程项目，不商业化 |
| 社会 | 可行 | 不碰真实资金；最小化收集；提供导出与删除；需隐私说明 |

**主要风险**：

1. 共享账本必须联网，服务器部署与运维是新增成本；
2. 账本内余额对成员透明，可能引发隐私顾虑；
3. 金额与权限规则多，测试成本高；
4. 课程周期紧，P1 需求可能被裁剪；
5. 用户可能把系统当作借贷凭证，需在协议中声明。

## 10. 验收标准

### 10.1 正常场景

- [ ] 注册登录后创建账本，生成 7 天有效邀请链接；
- [ ] 另一账号通过链接加入，能看到加入前的历史流水；
- [ ] 成员记录 100 元 3 人均分，分摊为 33.33/33.33/33.34，合计 100.00；
- [ ] 付款人不在参与人中时，余数给第一位参与人；
- [ ] 20 人账本结算方案不超过 19 笔转账；
- [ ] 付款方标记已转账、收款方确认后，该笔结清；
- [ ] 部分结清后，剩余金额可继续结算；
- [ ] Owner 导出全账本 CSV，表头和数据与页面一致；
- [ ] 成员只能导出自己的分摊流水；
- [ ] 账本归档后所有成员只能查看，不能编辑。

### 10.2 边界与异常场景

- [ ] 金额 0、负数、超过两位小数、超过 1,000,000：拒绝保存；
- [ ] 日期为明天或 366 天前：拒绝保存；
- [ ] 参与人为空或包含非成员：拒绝保存；
- [ ] 按比例合计 99.99% 或 100.01%：拒绝保存；
- [ ] 按金额合计与总额差 0.01：拒绝保存；
- [ ] 邀请码过期、被撤销、账本满 50 人：拒绝加入；
- [ ] 邀请码连续错误 5 次：锁定 10 分钟；
- [ ] 成员余额不为 0 时主动退出：拒绝并提示结算；
