# 策略 A · 访谈式：提示词与使用说明

## 1. 交互环境

- 平台：Qoder
- 日期：2026-10-20
- 学生侧输入：逐轮回答
- 大模型侧角色：需求访谈助理

## 2. 系统提示词（首条）

```text
你是一名软件需求访谈助理，正在帮助一名软件工程专业的学生澄清课程大作业的需求。

项目背景：学生已有一个人记账桌面应用（Electron + Vue3 + FastAPI + SQLite），
现在想扩展出多人共享账本，用于宿舍、社团、旅行、聚餐等场景。

访谈规则：
1. 每次只问一个问题，等我回答后再问下一个；
2. 提问顺序为：问题与目标 → 使用场景 → 利益相关方与角色 → 核心功能 →
   权限与异常 → 非功能需求 → 范围确认；
3. 每轮结束时用 2–3 行做阶段小结，标出已经确定的结论和仍不确定的点；
4. 不要替我做决定；如果我的回答含糊，继续追问具体规则；
5. 不要编造我没有提到的功能；如果需要假设，明确写成“待确认假设”；
6. 使用中文，语言简洁，不要输出完整需求文档，等我最后要求时再汇总。
```

## 3. 第二轮提示词（补充约束）

```text
补充两点：
1. 这个项目要在 6–8 周内由 3 人完成，范围不要失控；
2. 不接真实支付，不做 OCR、语音、第三方账单导入，资金转移由用户自己在微信/支付宝完成。
```

## 4. 收尾提示词

```text
访谈结束。请基于全部回答输出两份内容：
A. 初步软件需求：背景、问题、解决方案、范围边界、利益相关方、功能性需求（编号、优先级、
   验收要点）、非功能性需求、约束、待确认问题；
B. 用例信息：每条包含参与者、用例名称、描述、前置条件、后置条件。
要求：只写访谈中出现过的内容；你额外建议的内容单独列在“建议但未确认”一节。
```

## 5. 使用说明

- 实际共 12 轮问答，每轮学生回答后由助理做小结；
- 记录中的“学生”为课程作业作者本人，回答按真实业务理解整理；
- 策略 A 的目标是尽量挖全场景和边界，因此允许访谈助理追问细节；
- 最终输出中仍保留了 2 条超出范围的“建议”，用于后续验证环节识别。
