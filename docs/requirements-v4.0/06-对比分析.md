# 06 · 三种交互策略对比分析

## 1. 对比方法

- 同一原始构想、同一基线系统、同一模型；
- 三种策略独立执行，不共享中间输出；
- 统一用 `05-确认与验证.md` 中的 8 维评审和问题清单打分；
- 统计口径：功能需求按编号计；用例按独立用例计；边界场景按“权限、退出、退款、精度、并发、邀请、审计、注销、离线、预算、部分结清、删除恢复”等类别计。

## 2. 总览

| 指标 | A 访谈式 | B 一次性陈述 | C 多 Agent |
|---|---|---|---|
| 交互轮次 | 12 轮 | 2 次消息 | 3 个阶段 |
| 用时 | 约 40 分钟 | 约 5 分钟 | 约 25 分钟 |
| 功能需求数 | 19 | 14 | 21（含 3 条 P2） |
| 非功能需求数 | 8 | 6 | 9（含 1 条 P2） |
| 用例数 | 14 | 9 | 16 |
| 覆盖边界场景 | 8 类 | 3 类 | 12 类 |
| 幻觉/超范围条目 | 2 | 5 | 1（另 4 条过度设计） |
| 矛盾 | 1 | 3 | 1 |
| 遗漏 | 3 | 4 | 4 |
| 需求完整度（自评） | 85% | 55% | 92% |
| 可直接定稿 | 否 | 否 | 否 |

> 说明：完整度为按 8 维评审清单的自评，不是精确度量；主要用于相对比较。

## 3. 分维度对比

### 3.1 需求完整性

**A 访谈式（85%）**

- 优势：通过追问拿到了很多“只可意会”的规则，例如零头归属、24 小时编辑窗口、成员退出限制、部分结清、审计日志 180 天；
- 缺口：账号注销、邀请码限流、日志到期处理、退款与已结算关系；
- 特点：需求“有来源”，每条几乎都能对应到某一轮回答。

**B 一次性陈述（55%）**

- 优势：主干齐全，账号、账本、支出、分摊、结算、统计、预算、导出都有；
- 缺口：没有 Admin、退款、审计、并发、权限矩阵、账号注销；
- 特点：像“功能清单”，不像“可开发的需求”。

**C 多 Agent（92%）**

- 优势：三个用户角色覆盖了宿舍、个人、社团三种视角，评审代理又补了账号注销、邀请限流、日志到期等；
- 缺口：退款状态、Admin 边界、提醒对象、术语统一仍需修正；
- 特点：覆盖最全，但把“全面”误当成“都要做”。

### 3.2 幻觉与超范围

| 策略 | 典型幻觉 | 数量 | 原因 |
|---|---|---|---|
| A | 微信/支付宝账单自动导入、微信服务号推送 | 2 | 访谈助理“热心建议”，学生没有明确确认 |
| B | OCR 小票、语音记账、账单导入、微信支付自动扣款、区块链存证 | 5 | 单轮无法澄清，模型用自己的“最佳实践”填空 |
| C | 校园卡系统对接 | 1 | 用户代理提到“校园卡”后被分析师放大成系统对接 |

**结论**：交互越少，模型越倾向于用先验知识补全空白；多 Agent 也并不能消除幻觉，只是把幻觉集中到了“分析师补充”里。

### 3.3 边界场景覆盖

| 边界类型 | A | B | C |
|---|---|---|---|
| 权限边界（谁能改/删/移人） | 部分 | 缺失 | 完整 |
| 成员退出时余额 | 有（但自相矛盾） | 错误（余额清零） | 完整 |
| 退款与已结算 | 部分 | 缺失 | 有（但前置条件矛盾） |
| 分摊除不尽 | 完整 | 仅“两位小数” | 完整 |
| 并发修改 | 完整 | 缺失 | 完整 |
| 邀请过期/撤销/限流 | 部分 | 缺失 | 完整 |
| 审计与留痕 | 完整 | 缺失 | 完整 |
| 账号注销 | 缺失 | 缺失 | 完整 |
| 离线 | 完整 | 缺失 | 完整 |
| 预算提醒对象 | 缺失 | 模糊 | 完整 |
| 部分结清 | 完整 | 缺失 | 完整 |
| 删除恢复 | 完整 | 错误（不可恢复） | 完整 |

**结论**：共享账本的难点不在“记一笔”，而在“钱守恒、权限清、可追溯”。A 靠追问拿到了大部分隐式规则；B 完全没意识到这些规则；C 通过多角色提问把它们挖了出来。

### 3.4 效率

| 策略 | 人工投入 | 返工量 | 综合评价 |
|---|---|---|---|
| A | 高（40 分钟，12 轮） | 低（只需补 3 处遗漏） | 慢，但一次到位 |
| B | 低（5 分钟） | 高（几乎重写） | 快，但不可用 |
| C | 中（25 分钟，3 阶段） | 中（需要做减法和补漏） | 性价比最高 |

**关键观察**：B 节省的 35 分钟，在验证阶段以“重写 + 补漏”的方式全部还了回去。A 的前期投入换来了更少的返工。

### 3.5 缺陷类型

| 策略 | 主要缺陷 | 危害 |
|---|---|---|
| A | 过度建议、1 处自相矛盾 | 会把范围悄悄扩大；退出规则不一致会导致实现分歧 |
| B | 数据完整性错误、权限失控、隐私矛盾 | “退出余额清零”“任何人可删记录”会直接破坏账本可信度 |
| C | 过度设计、细节规则缺失 | CRDT、校园卡、最优算法、多租户会拖垮 6–8 周项目 |

### 3.6 差异原因分析

1. **交互方式决定信息密度**：访谈是“逐层剥洋葱”，能拿到 tacit knowledge；一次性陈述只能拿到显性功能；多 Agent 通过角色扮演制造了“多轮”，但没有真实追问，因此仍需人工裁决。
2. **模型有“补全冲动”**：当输入缺少规则时，模型会默认一个“合理”的做法。B 的“退出余额清零”就是模型为了简化流程而做的错误补全；A 的“自动导入”是模型为了让方案更完整而主动加戏。
3. **多 Agent 能查矛盾，但不能控范围**：评审代理擅长发现“退款前置条件与正文不符”“Admin 边界未定义”，但它不会主动说“这个项目不该做校园卡”，范围控制仍要靠人。
4. **金额与权限是高风险领域**：这类需求的隐含不变量多（金额守恒、权限最小化、操作可追溯），没有明确规则时，模型很容易给出“看起来合理但实际会丢钱/越权”的设计。
5. **学生的输入质量决定上限**：A 的回答包含大量真实约束（24 小时、7 天、50 人、180 天）；B 的草稿是“愿望清单”；C 把裁决权交给了 Agent，自己只在最后做取舍。

## 4. 成本—收益对比

| 策略 | 时间成本 | 需求完整度 | 返工成本 | 综合收益 |
|---|---|---|---|---|
| A | 40 min | 85% | 低 | 高 |
| B | 5 min | 55% | 高 | 低 |
| C | 25 min | 92% | 中 | 最高 |

**边际收益分析**：

- 从 B 到 A：多投入 35 分钟，完整度 +30 个百分点，返工大幅下降；
- 从 A 到 C：多投入的反而是“组织角色”的时间，完整度 +7 个百分点，但引入了 4 条过度设计；
- 最优组合不是单独使用某一种，而是：**C 负责查漏 → A 负责澄清 → B 的结构负责成稿**。

## 5. 最终选择

最终版本采用 **“A 为主线 + C 补漏 + B 的结构”**：

| 来源 | 进入最终版的内容 |
|---|---|
| A | 问题背景、范围边界、分摊规则、结算流程、权限雏形、非功能指标 |
| B | 文档结构、功能分组方式、精简表达 |
| C | 三视角诉求、账号注销、邀请限流、日志到期、Admin 边界、术语统一 |
| 人工裁决 | 删除全部超范围项；统一退出/退款/权限规则；补充验收标准 |

**不选择 B 的原因**：严重缺陷会破坏账本守恒和权限边界，修复成本高于重写。
**不直接选择 C 的原因**：覆盖虽全，但 4 条过度设计会把项目拖出 6–8 周的范围。
**不直接选择 A 的原因**：有 2 条幻觉和 3 处遗漏，需要 C 的评审补足。

## 6. 效度说明

- 本对比只针对“校园共享账本”一个题目、一个模型、一次执行，结论不能直接推广到所有需求场景；
- “完整度”是评审自评，存在主观性；
- 交互记录为课程作业的完整复现，时间与字数统计为估算；
- 不同模型、不同提示词版本可能得到不同结果，但“少交互 → 多幻觉”“多 Agent → 易过度设计”的趋势具有参考价值。
