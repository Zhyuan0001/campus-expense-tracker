> 说明：以下按阶段整理，保留各 Agent 的关键输出。

## 阶段 1 · 用户代理

### 1.1 宿舍长视角

**问题**：
1. 每次收水电费都要在群里翻谁交了、谁没交；
2. 聚餐有人不喝酒、有人带家属，均分不公平；
3. 月底结算要一个一个私聊，催款很尴尬。

**必须有的功能**：
1. 建账本、发链接拉人；
2. 记一笔就能选谁参与、怎么分；
3. 一键生成“谁该给谁多少”，并能标记谁已结清。

**最不能接受**：账算错、成员能看到我的手机号、有人偷偷改账。

**复杂度与提醒**：愿意学 10 分钟；提醒可以每天一次，但不要半夜发。

### 1.2 普通成员视角

**问题**：
1. 不知道自己这个月在该账本里花了多少、该付多少；
2. 别人记账时漏了我，或者把我算进了没参加的聚餐；
3. 群消息太多，结算通知经常被刷过去。

**必须有的功能**：
1. 一眼看到“我应付/我垫付/我该收”；
2. 每笔支出能看到付款人和参与人；
3. 结算时能确认，不是别人说我还了我就还了。

**最不能接受**：别人能随便改我的记录、我的个人账本被看到、频繁打扰。

**复杂度与提醒**：越简单越好；只在“有新支出涉及我”和“待我确认结算”时提醒。

### 1.3 社团财务视角

**问题**：
1. 社团一学期十几个人经手，换届后账目交接不清；
2. 活动结束后要按项目导出报销，Excel 经常对不上；
3. 有人误删或改数，最后说不清是谁改的。

**必须有的功能**：
1. 角色权限：财务、会长、普通成员权限不同；
2. 关键操作留痕，能查谁在什么时候改了什么；
3. 按活动/月份导出流水和汇总。

**最不能接受**：账目被无痕修改、换届后新财务看不到历史、数据丢失。

**复杂度与提醒**：可以接受 30 分钟学习；预算超支和待结算要提醒负责人。

### 1.4 用户代理小结

三个角色的共同点：都要“记得快、算得准、结得清、可追溯”。
主要冲突：
- 宿舍长想要“谁都能改，方便纠错”，普通成员担心“别人乱改”；
- 社团财务想要“报销审批”，但审批流超出本期范围；
- 普通成员不想被打扰，宿舍长和财务希望有催款/超支提醒。

## 阶段 2 · 分析师代理

### 2.1 冲突裁决

| 冲突 | 角色 A | 角色 B | 裁决 | 理由 |
|---|---|---|---|---|
| 记录修改权限 | 宿舍长：谁都能改 | 普通成员：不能被别人改 | 创建者 24h 内可改；Owner/Admin 可改任意记录；全部留痕 | 兼顾纠错与安全感 |
| 提醒频率 | 普通成员：越少越好 | 宿舍长/财务：要催款 | 默认只在“涉及我的新支出/待确认结算/预算超支”提醒；用户可关闭非结算提醒 | 结算类提醒不可关闭，避免赖账 |
| 报销审批 | 社团财务：需要审批 | 范围：不做审批 | 延后到 v5；v4.0 只做记账、导出、审计 | 控制范围 |
| 隐私与透明 | 普通成员：不想暴露联系方式 | 账本需要成员信息 | 账本内流水和余额对成员可见；手机/邮箱仅自己可见 | 对账必须透明，联系方式不必 |
| 管理员设置 | 宿舍长：不需要 | 社团财务：需要 | 保留 Admin 角色，由 Owner 授权 | 社团场景必需 |

### 2.2 分析师补充（角色未提，但需求完整所需）

1. 邀请链接有效期与人数上限；
2. 分摊金额的余数规则；
3. 退款与已结算记录的关系；
4. 成员退出时的余额处理；
5. 并发修改的冲突处理；
6. 账号注销与数据删除；
7. 审计日志保留期限；
8. 服务可用性与性能指标。

### 2.3 范围判断

- v4.0：账号、账本、成员与角色、支出、分摊、退款、结算、统计、预算、提醒、导出、审计；
- 延后：报销审批、真实支付、第三方账单导入、OCR、语音、多币种、公开社交；
- 建议但需评估：多端实时协同、校园卡对接、最优结算算法、多租户隔离（分析师标注为 P2，评审阶段处理）。

**学生确认**：同意裁决，进入评审阶段。

## 阶段 3 · 评审代理

### 3.1 评审发现（摘要）

| 编号 | 严重度 | 位置 | 问题 | 建议 |
|---|---|---|---|---|
| R-C-01 | 高 | 范围/外部系统 | “与校园卡系统对接”超出边界，且无授权渠道 | 删除 |
| R-C-02 | 高 | 非功能/协同 | “多端实时协同（CRDT）”与“离线只读、在线写入”的范围冲突 | 删除，保留版本冲突提示 |
| R-C-03 | 中 | 结算算法 | “理论最优结算”实现成本高，且用户感知差异小 | 改为“转账笔数 ≤ 成员数 − 1 的贪心方案” |
| R-C-04 | 中 | 账号 | 缺少账号注销规则，Owner 注销时账本如何处理未定义 | 补充 |
| R-C-05 | 中 | 邀请 | 邀请码未定义尝试次数限制，存在暴力猜测风险 | 补充限流 |
| R-C-06 | 中 | 退款 | 退款与“已结算”状态的关系不清 | 补充：已结算支出不可退款 |
| R-C-07 | 中 | 权限 | Admin 能否移除其他 Admin 未定义 | 补充：不能 |
| R-C-08 | 低 | 提醒 | “提醒负责人”未定义负责人范围 | 明确为 Owner/Admin |
| R-C-09 | 低 | 审计 | 日志保留期未量化 | 设为 180 天 |
| R-C-10 | 低 | 术语 | “账本/群组/项目”混用 | 统一为“账本” |

### 3.2 评审代理总结

- 需求整体覆盖了三个角色的核心诉求，边界场景比单 Agent 更全；
- 主要风险不是遗漏，而是**过度设计**：分析师把“实时协同、校园卡、最优算法、多租户”写进了 P2，容易拖垮 6–8 周的项目；
- 权限和退款规则仍有 4 处需要明确；
- 建议在定稿时删除 R-C-01、R-C-02，降级 R-C-03，并补齐 R-C-04 至 R-C-09。

**学生裁决**：
- 采纳 R-C-01、R-C-02：删除；
- 采纳 R-C-03：改为贪心结算；
- 采纳 R-C-04 至 R-C-09：补入需求；
- R-C-10：统一术语；
- 保留“多租户隔离”作为远期设想，不进入 v4.0。
