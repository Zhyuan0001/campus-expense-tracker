## 2. 八维评审

| 维度 | 检查问题 | 策略 A | 策略 B | 策略 C |
|---|---|---|---|---|
| 中肯性 | 是否反映真实问题、有意义 | 通过：问题来自宿舍/社团真实场景 | 部分失败：加入区块链、微信支付等无关内容 | 通过：三视角均围绕记账与结算 |
| 合理性 | 解决方案是否科学合理 | 通过：只记录不转账，边界合理 | 失败：“退出余额清零”违背账本守恒 | 通过：方案合理，但含过度设计 |
| 完整性 | 是否覆盖利益相关方期望 | 较好：缺账号注销、邀请限流、日志到期 | 差：缺退款、角色、审计、并发 | 最好：覆盖三视角，但仍有细节缺口 |
| 必要性 | 每项需求是否必要 | 2 项超范围（自动导入、微信推送） | 5 项超范围（OCR、语音、导入、微信支付、区块链） | 4 项过度设计（CRDT、校园卡、最优算法、多租户） |
| 溯源性 | 是否有明确来源 | 较好：可追溯到访谈轮次 | 差：大量默认假设未标注 | 较好：标注角色来源，分析师补充单独标出 |
| 准确性 | 描述是否清晰准确 | 较好：多数规则可验证 | 差：“响应快”“安全”等不可测 | 较好：多数量化，个别术语混用 |
| 正确性 | 是否反映提出者真实想法 | 较好，但 FR-A-06 与 UC-A-10 对退出规则表述不一致 | 差：把“随便说说”当成确定需求 | 较好：能区分角色诉求与分析师补充 |
| 一致性 | 文档、用例、原型是否一致 | 1 处矛盾（退出规则） | 3 处矛盾（删除权限、退出余额、公开/私有） | 1 处矛盾（退款前置条件），术语不统一 |

**结论**：三份初稿都不能直接定稿。A 的领域深度最好，B 的效率最高但质量不合格，C 的覆盖面最广但需要做减法。

## 4. 六类可行性分析

### 4.1 技术可行性

| 技术点 | 判断 | 说明 |
|---|---|---|
| 账号与鉴权 | 可行 | FastAPI + JWT/Session，成熟方案 |
| 账本与权限 | 可行 | 关系型表结构即可表达 |
| 分摊与结算 | 可行 | 金额按分计算；贪心结算复杂度 O(n log n) |
| 实时提醒 | 可行 | 站内轮询或 WebSocket；本期建议轮询 |
| 凭证图片 | 可行 | 对象存储或本地文件；需限制大小与类型 |
| CRDT 实时协同 | 不做 | 与离线只读约束冲突，成本高 |
| 校园卡对接 | 不做 | 无授权渠道 |
| OCR/语音/第三方账单导入 | 不做 | 超出课程范围 |
| 区块链存证 | 不做 | 与问题无关，成本高 |

### 4.2 设备可行性

- 开发：现有 Linux/Windows 开发机即可；
- 部署：需要一台可访问的服务器或校园内网主机，用于账号与共享数据；
- 测试：桌面浏览器 + 手机浏览器（360px 宽度）；
- 不需要额外硬件、支付终端或校园卡读卡器。

### 4.3 进度可行性

- 周期 6–8 周，3 人；
- 建议拆分：账号与账本 2 周、支出与分摊 2 周、结算与统计 2 周、联调与测试 1–2 周；
- 原型只覆盖核心流程，不追求视觉打磨；
- 风险：如果坚持做实时协同或第三方导入，进度必然失控。

### 4.4 成本可行性

- 无付费 API；服务器可用课程/校园资源或低配云主机；
- 对象存储若使用本地磁盘，成本可忽略；
- 主要成本是人力与联调时间；
- 不接真实支付，避免资金与合规成本。

### 4.5 商业可行性

- 课程项目不以盈利为目标；
- 对学生群体有真实使用价值，可作为作品集；
- 不依赖付费获客，不涉及广告与信贷。

### 4.6 社会可行性

- 符合个人信息保护的最小化原则：只收集昵称、登录标识和账本数据；
- 不处理真实资金，降低金融风险；
- 需要提供数据导出与删除能力；
- 账本内余额对成员可见是业务必需，但联系方式必须隐藏；
- 需在用户协议中说明“本系统不构成借贷凭证”。

**结论**：核心范围技术、设备、进度、成本、商业、社会六类均可行；被删除的 8 项（自动导入、微信推送、OCR、语音、微信支付、区块链、CRDT、校园卡）均存在可行性或范围问题。

## 6. 验证结论

1. **策略 A**：领域理解最好，边界场景较全，但有 2 条幻觉、1 条矛盾和 3 处遗漏，不能直接定稿；
2. **策略 B**：效率最高，但 7 条严重问题，其中“退出余额清零”“任何人可删记录”会破坏账本一致性，判定为不合格；
3. **策略 C**：覆盖面最广，评审代理有效发现了 A/B 的多个问题，但自身有 4 条过度设计，适合作为“查漏工具”而非“定稿工具”；
4. **最终策略**：以 A 为业务主线，以 C 的评审意见补漏，以 B 的结构作为文档组织参考，删除全部超范围内容，形成 `07-最终版`。

## 7. 剩余风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 共享账本需要服务端，部署方式未定 | 影响可用性与成本 | 在设计与实现阶段确定校园服务器或云主机 |
| 原始构想假设“在线写入” | 弱网体验差 | 明确离线只读，后续版本再考虑离线队列 |
| 账本内余额透明可能引发隐私顾虑 | 用户接受度 | 在加入账本时明确告知，联系方式仍隐藏 |
| 课程演示数据与真实数据混用 | 演示风险 | 提供独立的演示账本与一键重置 |
| 需求范围仍偏大 | 进度风险 | 按 P0 → P1 顺序实现，P2 一律不做 |
