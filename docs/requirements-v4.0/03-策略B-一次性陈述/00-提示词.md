# 策略 B · 一次性陈述：提示词与使用说明

## 1. 交互环境

- 平台：Qoder
- 日期：2026-10-20
- 交互轮次：1 轮主请求 + 1 次格式补充，全程不追问
- 目的：测试“学生一次性给出全部想法，模型一次性审查补全”的效率与风险

## 2. 主提示词（原文）

```text
你是资深软件需求分析师。我要在现有的校园记账系统上增加共享账本，用于宿舍、社团、
旅行和聚餐。现有系统是 Electron + Vue3 + FastAPI + SQLite 的单人记账应用。

以下是我能想到的全部需求，请你审查、补全并整理成初步需求文档：
1. 可以创建账本，把室友拉进来，发链接就能加入；
2. 每个人都能记账，记金额、分类、日期、谁付的钱、谁参与；
3. 可以 AA，也可以按比例或按金额分；
4. 系统自动算谁欠谁；
5. 结算后能标记已还；
6. 账本里能看统计，也能导出；
7. 记录可以删，谁都能删，简单一点；
8. 成员可以随时退出；
9. 可以设预算；
10. 要有提醒；
11. 数据要安全，只有成员能看；
12. 最好能自动导入支付宝/微信账单，能识别小票，能语音记账。

请直接输出：
A. 初步需求（功能需求、非功能需求、约束）；
B. 用例信息（参与者、用例名称、描述、前置条件、后置条件）。

不用问我问题，按你的专业判断补全即可。
```

## 3. 第二次提示词（仅要求整理格式）

```text
把上面的内容整理成 Markdown 表格，编号统一，功能需求用 FR-B-xx，非功能需求用 NFR-B-xx。
```

## 4. 使用说明

- 策略 B 刻意**不允许追问**，以观察模型在信息不足时的默认假设；
- 学生的草稿保留口语化、矛盾和不完整之处，不预先修正；
- 模型补全的内容全部保留，包括它自行加入的技术方案；
- 这些内容将在 `05-确认与验证.md` 中逐条审查。
