# 01 · 软件原始构想

## 1. 一句话构想

在现有校园记账系统的基础上增加「搭子账本」：让宿舍、社团、旅行、聚餐等多人场景可以**共同记账、自动分摊、一键结算**，把原本散落在微信群和 Excel 里的共同开销变成一本有账可查、有据可依的共享账本。

## 2. 基线系统

本构想不是从零开始，而是基于任务01《校园消费记账系统》v3.1.0 扩展。

| 已有能力 | 现状 |
|---|---|
| 个人记账 | 金额、分类、描述、日期，支持编辑与删除 |
| 查询筛选 | 按年月、关键字、分类、金额区间筛选 |
| 统计 | 月度总额、分类占比、图表 |
| 预算 | 月度总预算，80%/100% 三色提醒 |
| 分类管理 | 默认 8 类，可增删自定义分类 |
| 数据 | CSV 导出、JSON 备份与恢复 |
| 形态 | Electron 桌面端 + FastAPI 后端 + SQLite，本地单用户 |

**关键限制**：现有系统是单用户、单机、无账号体系，所有数据只属于一个人。共享账本必须先补齐“人、账本、成员关系、权限”四类基础概念。

## 3. 要解决的问题

### 3.1 场景观察

大学生常见的共同开销场景：

- 宿舍：水电费、日用品、聚餐、公共设备；
- 社团：活动物料、场地费、交通费、报销；
- 旅行：车票、住宿、门票、餐饮，往往一人先垫付；
- 小组/班级：打印、班费、集体活动。

### 3.2 现有做法与痛点

| 编号 | 痛点 | 具体表现 |
|---|---|---|
| P1 | 记账分散 | 费用记在微信群、备忘录、Excel、截图里，时间一长找不到 |
| P2 | 漏记重记 | 谁垫付、谁参与、是否已还，靠记忆和聊天记录，容易遗漏或重复 |
| P3 | 分摊易错 | AA、按比例、按人头、有人不参与等规则混用，手算容易出错 |
| P4 | 结算麻烦 | 多人互相欠款，转账链路长，算不清“谁该给谁多少” |
| P5 | 催款尴尬 | 不好意思反复催，结清状态不透明，容易产生误会 |
| P6 | 权限缺失 | 社团经费多人经手，谁改了账、谁删了记录说不清 |
| P7 | 个人账失真 | 共同开销混进个人账本，个人消费统计和预算被污染 |

### 3.3 问题界定

本软件要解决的不是“支付”问题，而是**共同消费的记录、分摊、对账和结清确认**问题。真实资金转移仍由微信、支付宝、银行卡等外部工具完成，软件只负责记账和状态确认。

## 4. 基于软件的解决方案

### 4.1 核心方案

1. 引入账号体系与共享账本，一本账本对应一个多人消费场景；
2. 每笔共同支出记录**付款人、参与人、金额、分摊方式、凭证**；
3. 系统按规则自动计算每个人的“应付”和“垫付”，得出净余额；
4. 系统生成“谁转给谁、转多少”的结算建议，双方确认后结清；
5. 通过角色权限、操作日志和数据导出，保证多人经手也能追溯；
6. 保留个人账本，共享账本与个人账本分开统计，避免互相污染。

### 4.2 与现有系统的关系

- 个人记账、预算、统计、分类、导出等能力**继承**；
- 共享账本是新增模块，复用分类体系和统计口径；
- 现有 SQLite 数据结构需要扩展，但本任务只做需求，不涉及实现。

## 5. 范围与边界

### 5.1 范围内（v4.0 要做）

| 模块 | 内容 |
|---|---|
| 账号 | 注册、登录、退出、找回密码、个人资料 |
| 账本 | 创建、查看、归档、删除 |
| 成员 | 邀请、加入、退出、移除、转让创建者、设置管理员 |
| 共同支出 | 新增、编辑、删除、退款、凭证图片 |
| 分摊 | 均分、按金额、按比例；金额精确到分 |
| 结算 | 余额计算、结算建议、部分结清、结清确认、结算历史 |
| 统计 | 账本流水、按月/分类/成员统计、个人垫付与应付 |
| 预算 | 账本共享预算、超支提醒 |
| 提醒 | 站内提醒：新支出、待结算、预算超支 |
| 数据 | CSV 导出、JSON 备份、账本级导出 |
| 审计 | 关键操作日志，创建者/管理员可查 |

### 5.2 范围外（v4.0 不做）

| 不做项 | 原因 |
|---|---|
| 真实支付、自动扣款、代收代付 | 涉及金融资质与资金安全，课程项目不碰 |
| 银行、微信、支付宝账单自动导入 | 接口与格式不稳定，且需要授权 |
| OCR 小票识别、语音记账 | 技术成本高，不是本期核心问题 |
| 多币种、汇率换算 | 校园场景以人民币为主 |
| 公开社交、账本广场、聊天 | 偏离记账与结算目标 |
| 短信、邮件、系统推送 | 本期只做站内提醒，避免额外服务依赖 |
| 离线写入与多人实时协同 | 需要冲突合并机制，本期只保证在线写入、离线只读缓存 |
| 运营后台、广告、信贷 | 非课程目标 |

### 5.3 系统边界

```
┌─────────────────────────────┐
│        搭子账本系统          │
│  账号 / 账本 / 成员 / 支出   │
│  分摊 / 结算 / 统计 / 预算   │
└──────────┬──────────────────┘
           │ 只记录与确认，不转移资金
┌──────────▼──────────────────┐
│ 微信 / 支付宝 / 银行卡       │  ← 外部系统，用户自行完成转账
└─────────────────────────────┘
```

## 6. 利益相关方

| 利益相关方 | 角色 | 主要诉求 | 关注点 |
|---|---|---|---|
| 学生用户 | 普通成员 | 快速记账、看清自己该付多少 | 操作简单、金额准确 |
| 宿舍长 / 社团财务 / 旅行发起人 | 账本创建者 | 管好成员和账目、能对账 | 权限、导出、审计 |
| 被授权的老成员 | 账本管理员 | 协助管理成员和记录 | 权限边界清晰 |
| 被邀请的同学 | 访客 / 新成员 | 不用学习就能加入和查看 | 邀请简单、隐私可控 |
| 开发者 / 维护者 | 开发团队 | 需求明确、可迭代 | 技术可行性、兼容现有系统 |
| 系统管理员 | 运维 | 账号安全、数据可恢复 | 备份、日志、故障处理 |
| 学校 / 监管方 | 外部约束 | 个人信息保护、数据合规 | 最小化收集、可删除 |

## 7. 目标与成功标准

| 目标 | 可验证标准 |
|---|---|
| 记账快 | 熟练用户 30 秒内完成一笔共同支出；新用户 3 分钟内完成首笔 |
| 分摊准 | 任意分摊方式下，Σ成员应付 = 支出金额，误差为 0（精确到分） |
| 结算清 | 20 人账本生成的转账笔数不超过 19 笔；结清状态可追溯 |
| 权限严 | 非成员无法查看账本；普通成员无法执行管理员操作 |
| 数据稳 | 已确认的支出不丢失；故障后 10 分钟内恢复 |
| 易上手 | 新用户无需培训，5 分钟内完成“加入账本—记一笔—看结算” |

## 8. 约束

| 类别 | 约束 |
|---|---|
| 技术 | 沿用 Electron + Vue 3 + TypeScript + FastAPI + SQLite；新增账号与服务端能力 |
| 数据 | 人民币、精确到分；日期按 Asia/Shanghai；金额不允许为 0 或负数（退款用独立类型） |
| 界面 | 中文；桌面端为主，兼容 360px 以上移动浏览器 |
| 团队 | 课程项目，3 人左右，周期约 6–8 周 |
| 合规 | 只收集必要信息；密码加密存储；支持导出与删除个人数据 |
| 外部依赖 | 不接真实支付、不做短信/邮件服务 |

## 9. 需求六要素的初步回答

| 要素 | 初步回答 |
|---|---|
| Who | 学生成员、账本创建者、管理员、被邀请者、运维人员 |
| What | 共享账本、共同支出、分摊、结算、统计、预算、权限与审计 |
| Why | 解决多人共同消费记不清、算不准、结不清的问题 |
| Where | 账本模块、支出模块、结算模块、统计模块、成员与权限模块 |
| How | 记录付款人与参与人，按规则分摊，计算净余额，生成结算建议并确认 |
| When | 宿舍/社团/旅行等共同消费发生时；月末、活动结束后结算时 |

## 10. 交给后续策略澄清的问题

1. 账本创建者、管理员、普通成员分别能做什么？
2. 邀请用链接还是邀请码？有效期和人数上限是多少？
3. 分摊除不尽时，余数归谁？
4. 支出记录谁能改、谁能删？改删后如何留痕？
5. 成员退出时还有未结清余额怎么办？
6. 退款是整单退还是可以部分退？如何冲销分摊？
7. 结算由谁发起、谁确认？能否部分结清？
8. 共享预算由谁设置？超支提醒发给谁？
9. 离线能不能记账？多端同时修改同一条记录怎么办？
10. 个人账本和共享账本的数据如何隔离？
