# 从一句想法到可校验需求：共享账本需求获取的三次 AI 实验

> 课程：软件工程 · 第六讲《软件需求获取》
> 日期：2026-10-20
> 基线：校园消费记账系统 v3.1.0
> 仓库：https://github.com/Zhyuan0001/campus-expense-tracker/tree/master/docs/requirements-v4.0

## 摘要

这次作业，我在已有的校园个人记账系统上扩展出一个「搭子账本」：宿舍、社团、旅行、聚餐时，多人可以共同记账、自动分摊、一键结算。

需求获取用了三种与大模型交互的策略：

| 策略 | 形式 | 产出 | 结论 |
|---|---|---|---|
| A 访谈式 | 12 轮逐问逐答 | 19 条功能需求、8 条非功能需求、14 个用例 | 规则最完整，但耗时，且有 2 条幻觉 |
| B 一次性陈述 | 1 轮审查补全 | 14 条功能需求、6 条非功能需求、9 个用例 | 效率最高，但发现 5 条幻觉、3 条矛盾，不可用 |
| C 多 Agent | 用户代理 → 分析师 → 评审者 | 21 条功能需求、9 条非功能需求、16 个用例 | 覆盖最全，但有 4 条过度设计 |

最终版采用「A 为主线 + C 补漏 + B 的结构」，删除全部超范围内容，形成 **19 条功能需求、9 条非功能需求、17 个用例**，并做了可点击原型。

一句话结论：**AI 很适合做结构化、补场景、查矛盾，但不能替人做范围控制和业务规则裁决。**

## 一、为什么选这个题

前几个任务里，我已经做了一个校园个人记账系统：记录消费、分类统计、月度预算、导出备份，技术栈是 Electron + Vue 3 + FastAPI + SQLite。它解决的是“一个人怎么记账”。

但大学生真实的花钱场景往往不是一个人：

- 宿舍交水电费、买日用品、聚餐；
- 社团买物料、租场地、打车；
- 旅行订民宿、买门票，通常一个人先垫；
- 班级/小组打印、班费、集体活动。

现在的做法通常是“一个人先垫，群里发红包，月底用 Excel 算”。痛点很集中：

| 编号 | 痛点 | 具体表现 |
|---|---|---|
| P1 | 记录分散 | 费用散在微信群、备忘录、Excel、截图里 |
| P2 | 漏记重记 | 谁垫付、谁参与、是否已还，靠记忆和聊天记录 |
| P3 | 分摊易错 | AA、按比例、按人头混用，手算容易错 |
| P4 | 结算麻烦 | 多人互相欠款，转账链路长 |
| P5 | 催款尴尬 | 不好意思反复催，结清状态不透明 |
| P6 | 权限缺失 | 社团经费多人经手，谁改了账说不清 |
| P7 | 个人账失真 | 共同开销混进个人账本，统计和预算被污染 |

所以原始构想是：在现有记账系统上增加「搭子账本」，只做**共同消费的记录、分摊、对账和结清确认**。真实资金转移仍由用户在微信/支付宝完成，平台不碰钱。

### 范围边界

**范围内**：账号、账本、成员与角色、共同支出、分摊、退款、结算、统计、共享预算、站内提醒、导出备份、审计日志、账号注销。

**范围外**：真实支付、自动扣款、第三方账单导入、OCR、语音记账、区块链、多币种、公开社交、短信/邮件/微信推送、离线写入、CRDT、校园卡对接、社团报销审批、多租户、运营后台。

完整原始构想见：[01-原始构想.md](https://github.com/Zhyuan0001/campus-expense-tracker/blob/master/docs/requirements-v4.0/01-%E5%8E%9F%E5%A7%8B%E6%9E%84%E6%83%B3.md)。

## 二、实验设计：同一构想，三种交互策略

三种策略使用同一个原始构想、同一个基线系统、同一个模型，互不共享中间输出。

| 策略 | 谁在提问 | 交互轮次 | 预期优势 | 预期风险 |
|---|---|---|---|---|
| A 访谈式 | 大模型扮演访谈助理 | 12 轮 | 能挖出隐式规则和边界 | 慢；助理可能“加戏” |
| B 一次性陈述 | 学生一次性写全 | 1 轮 | 快；结构完整 | 信息不足时模型会脑补 |
| C 多 Agent | 用户代理、分析师、评审者 | 3 阶段 | 多视角、能查矛盾 | 容易过度设计 |

验证阶段统一用 8 个维度：中肯性、合理性、完整性、必要性、溯源性、准确性、正确性、一致性；再做技术、设备、进度、成本、商业、社会六类可行性分析。

## 三、策略 A：访谈式，像剥洋葱一样问出规则

### 3.1 系统提示词

```text
你是一名软件需求访谈助理，正在帮助一名软件工程专业的学生澄清课程大作业的需求。

项目背景：学生已有一个人记账桌面应用（Electron + Vue3 + FastAPI + SQLite），
现在想扩展出多人共享账本，用于宿舍、社团、旅行、聚餐等场景。

访谈规则：
1. 每次只问一个问题，等我回答后再问下一个；
2. 提问顺序为：问题与目标 → 使用场景 → 利益相关方与角色 → 核心功能 →
   权限与异常 → 非功能需求 → 范围确认；
3. 每轮结束时用 2–3 行做阶段小结，标出已经确定的结论和仍不确定的点；
4. 不要替我做决定；如果我的回答含糊，继续追问具体规则；
5. 不要编造我没有提到的功能；如果需要假设，明确写成“待确认假设”；
6. 使用中文，语言简洁，不要输出完整需求文档，等我最后要求时再汇总。
```

### 3.2 12 轮访谈的关键结论

| 轮次 | 访谈焦点 | 关键回答 / 决定 |
|---|---|---|
| 1 | 现状与痛点 | 宿舍、社团、旅行、聚餐；微信群 + 红包 + Excel；漏记、对账难 |
| 2 | 场景优先级 | 覆盖 2–50 人；社团只做共同支出和结算，不做报销审批 |
| 3 | 角色分层 | Owner、Admin、Member、Guest；Admin 不能移除 Admin 或 Owner |
| 4 | 邀请与加入 | 链接 + 6 位邀请码；7 天有效；可撤销；最多 50 人；加入后可看历史 |
| 5 | 支出字段 | 金额、分类、备注、日期、付款人、参与人、分摊方式、凭证；金额 >0，两位小数；日期不晚于今天、不早于一年前 |
| 6 | 分摊与零头 | 均分、按金额、按比例；算到分；余数优先给付款人，付款人不参与时给第一位参与人；比例合计 100%，金额合计等于总额 |
| 7 | 修改/删除/退款 | 创建者 24 小时内可改；Owner/Admin 可改任意记录；软删除；已结算不可改删；只做整单退款；退款后原支出锁定 |
| 8 | 结算流程 | 系统算净额并给转账建议；付款方标记已转账，收款方确认到账；支持部分结清；争议可拒绝；结算历史不可删 |
| 9 | 退出/转让/生命周期 | 余额为 0 才能主动退出；Owner 可强制移出并承接余额；Owner 可转让；归档只读；删除需余额为 0 + 30 天回收站 |
| 10 | 权限与隐私 | 成员可见账本流水和余额；个人账本互不可见；联系方式默认隐藏；导出和审计按角色控制 |
| 11 | 非功能需求 | 账本 1s 内打开；500 条流水 1s；20 人结算 2s；99% 可用；故障 10 分钟恢复；密码 5 次错误锁 10 分钟；审计 180 天；离线只读；并发冲突提示 |
| 12 | 范围确认 | 真实支付、自动导入、OCR、语音、多币种、公开社交、外部推送、离线写入、报销审批都不做 |

### 3.3 策略 A 的产出与问题

产出：19 条功能需求、8 条非功能需求、14 个用例。

优点：

- 拿到了很多“只可意会”的规则，例如零头归属、24 小时编辑窗口、成员退出限制、部分结清、审计日志 180 天；
- 每条需求几乎都能追溯到某一轮回答；
- 非功能指标比较具体，能直接写进验收标准。

问题：

- 访谈助理主动加了两条我没有确认过的需求：自动导入微信/支付宝账单、微信服务号推送；
- FR-A-06 写“成员可随时退出”，但 UC-A-10 的前置条件写“余额为 0”，同一份文档内自相矛盾；
- 漏了账号注销、邀请码限流、日志到期处理。

## 四、策略 B：一次性陈述，5 分钟出稿，但几乎要重写

### 4.1 主提示词

```text
你是资深软件需求分析师。我要在现有的校园记账系统上增加共享账本，用于宿舍、社团、
旅行和聚餐。现有系统是 Electron + Vue3 + FastAPI + SQLite 的单人记账应用。

以下是我能想到的全部需求，请你审查、补全并整理成初步需求文档：
1. 可以创建账本，把室友拉进来，发链接就能加入；
2. 每个人都能记账，记金额、分类、日期、谁付的钱、谁参与；
3. 可以 AA，也可以按比例或按金额分；
4. 系统自动算谁欠谁；
5. 结算后能标记已还；
6. 账本里能看统计，也能导出；
7. 记录可以删，谁都能删，简单一点；
8. 成员可以随时退出；
9. 可以设预算；
10. 要有提醒；
11. 数据要安全，只有成员能看；
12. 最好能自动导入支付宝/微信账单，能识别小票，能语音记账。

请直接输出初步需求和用例信息。不用问我问题，按你的专业判断补全即可。
```

### 4.2 模型替我做的大量默认假设

| 未确认点 | 模型默认假设 | 真实意图 |
|---|---|---|
| 邀请链接 | 永久有效、人数不设上限 | 7 天过期、最多 50 人、可撤销 |
| 删除权限 | 所有成员可删任意记录、不可恢复 | 角色 + 24 小时 + 软删除 + 审计 |
| 成员退出 | 退出后未结清余额自动清零 | 余额不为 0 禁止退出 |
| 管理员 | 不设管理员，创建者全管 | 社团需要管理员 |
| 提醒渠道 | 站内 + 微信服务号推送 | 只做站内 |
| 智能录入 | OCR、语音、自动导入账单 | 不做 |
| 数据可信 | 区块链存证 | 不做 |
| 支付 | 微信支付自动扣款 | 绝对不做 |

### 4.3 最严重的几条错误

**错误一：所有成员可删除任意记录**

> 所有成员可编辑和删除任意记录；删除后不可恢复。

普通成员可以删别人的账，且无法追溯，和“数据安全”目标完全冲突。

**错误二：退出后余额自动清零**

> 成员可随时退出账本，退出后其未结清余额自动清零。

余额不会凭空消失。清零等于把债务转嫁给其他成员，直接违反金额守恒。

**错误三：邀请链接永久有效**

> 邀请链接永久有效，可多人使用，人数不设上限。

链接一旦泄露就无法收回，账本可能被陌生人加入。

**错误四：隐私规则自相矛盾**

> 账本默认公开可搜索；同时只有账本成员能查看账本内容。

**错误五：大量超范围技术**

OCR 小票、语音记账、微信支付自动扣款、区块链存证，全部超出课程范围和技术可行性。

### 4.4 策略 B 的产出与结论

产出：14 条功能需求、6 条非功能需求、9 个用例。

结论：效率最高（约 5 分钟），但确认与验证阶段发现了 5 条幻觉/超范围、3 条矛盾、4 处关键遗漏，判定为不合格。B 省下的 35 分钟，后来以“重写 + 补漏”的方式全部还了回去。

## 五、策略 C：多 Agent，查漏很强，做减法很弱

### 5.1 编排提示词

```text
接下来你将依次扮演三个 Agent，完成共享账本的需求获取。每个阶段结束时暂停，
等我确认后再进入下一阶段。三个 Agent 的职责必须严格分开：

Agent 1 用户代理：分别扮演宿舍长、普通成员、社团财务，提出各自视角的诉求；
Agent 2 分析师代理：合并三方诉求，形成初步需求与用例，标注来源和冲突裁决；
Agent 3 评审代理：只挑错，不重写需求，从完整性、一致性、可行性、可测试性、
范围控制五个维度输出问题清单。
```

### 5.2 三个用户角色的诉求

| 角色 | 最常遇到的问题 | 必须有的功能 | 最不能接受 |
|---|---|---|---|
| 宿舍长 | 收水电费要翻群、聚餐均分不公平、催款尴尬 | 建账拉人、选参与人分摊、一键结算 | 账算错、联系方式泄露、有人偷改账 |
| 普通成员 | 不知道自己该付多少、被漏记/被多算、通知被刷过去 | 看应付/垫付/应收、看付款人和参与人、结算确认 | 别人随便改我的记录、个人账被看到、频繁打扰 |
| 社团财务 | 多人经手、换届交接不清、报销导出对不上 | 角色权限、操作留痕、按活动/月份导出 | 无痕修改、换届后看不到历史、数据丢失 |

### 5.3 分析师代理的冲突裁决

| 冲突 | 角色 A | 角色 B | 裁决 |
|---|---|---|---|
| 记录修改权限 | 宿舍长：谁都能改 | 普通成员：不能被别人改 | 创建者 24h 内可改；Owner/Admin 可改任意记录；全部留痕 |
| 提醒频率 | 普通成员：越少越好 | 宿舍长/财务：要催款 | 只提醒“涉及我的新支出/待确认结算/预算超支”；结算提醒不可关 |
| 报销审批 | 社团财务：需要 | 范围：不做审批 | 延后到 v5；v4.0 只做记账、导出、审计 |
| 隐私与透明 | 普通成员：不想暴露联系方式 | 账本需要成员信息 | 流水和余额对成员可见；手机/邮箱仅自己可见 |
| 管理员设置 | 宿舍长：不需要 | 社团财务：需要 | 保留 Admin 角色，由 Owner 授权 |

### 5.4 评审代理发现的 10 个问题

| 编号 | 严重度 | 问题 | 处理 |
|---|---|---|---|
| R-C-01 | 高 | 校园卡系统对接超出边界且无授权 | 删除 |
| R-C-02 | 高 | CRDT 多端实时协同与“离线只读、在线写入”冲突 | 删除，保留版本冲突提示 |
| R-C-03 | 中 | “理论最优结算”实现成本高、收益低 | 改为贪心方案，笔数 ≤ 成员数 − 1 |
| R-C-04 | 中 | 账号注销时 Owner 身份和未结清余额处理不清 | 补充前置条件与匿名化规则 |
| R-C-05 | 中 | 邀请码限流没有具体阈值 | 量化为 5 次/10 分钟 |
| R-C-06 | 中 | 退款与“已结算”关系不清 | 明确已结算不可退款 |
| R-C-07 | 中 | Admin 能否移除其他 Admin 未定义 | 补充：不能；可自行退出管理员身份 |
| R-C-08 | 低 | “提醒负责人”范围不清 | 明确预算提醒只发 Owner/Admin |
| R-C-09 | 低 | 审计日志到期后的处理未定义 | 补充归档与清理规则 |
| R-C-10 | 低 | “账本/群组/项目”术语混用 | 统一为“账本” |

### 5.5 策略 C 的产出与问题

产出：21 条功能需求、9 条非功能需求、16 个用例。

优点：三个用户角色覆盖了宿舍、个人、社团三种视角；评审代理能发现单 Agent 漏掉的矛盾，例如退款前置条件、Admin 边界、账号注销、邀请限流。

问题：分析师把“实时协同、校园卡、最优算法、多租户”写进了 P2，容易拖垮 6–8 周的项目。多 Agent 不能替代范围控制，它只适合当“查漏工具”。

## 六、三种策略的对比

### 6.1 总览

| 指标 | A 访谈式 | B 一次性陈述 | C 多 Agent |
|---|---|---|---|
| 交互轮次 | 12 轮 | 1 轮 | 3 阶段 |
| 用时 | 约 40 分钟 | 约 5 分钟 | 约 25 分钟 |
| 功能需求 | 19 | 14 | 21（含 3 条 P2） |
| 非功能需求 | 8 | 6 | 9（含 1 条 P2） |
| 用例 | 14 | 9 | 16 |
| 边界场景 | 8 类 | 3 类 | 12 类 |
| 幻觉/超范围 | 2 | 5 | 1（另 4 条过度设计） |
| 矛盾 | 1 | 3 | 1 |
| 遗漏 | 3 | 4 | 4 |
| 完整度（自评） | 85% | 55% | 92% |
| 能否直接定稿 | 否 | 否 | 否 |

### 6.2 五个维度的差异

**完整性**

- A：靠追问拿到了大量隐式规则，但漏了账号注销、邀请限流、日志到期；
- B：主干齐全，但缺 Admin、退款、审计、并发、权限矩阵、账号注销；
- C：三个角色 + 评审代理，覆盖最全，但把“全面”误当成“都要做”。

**幻觉**

- A：2 条，主要是访谈助理“热心建议”的自动导入和微信推送；
- B：5 条，模型用自己的“最佳实践”填空；
- C：1 条（校园卡对接），另有 4 条过度设计。

**边界覆盖**

- A：8 类，包括退出、退款、精度、并发、邀请、审计、离线、部分结清；
- B：3 类，几乎没有意识到金额守恒和权限边界；
- C：12 类，通过多角色和多轮评审把大部分异常挖了出来。

**效率**

- B 最快，但返工量最大；
- A 最慢，但一次到位；
- C 居中，性价比最高，但需要人工做减法和补漏。

**缺陷类型**

- A：过度建议 + 1 处自相矛盾；
- B：数据完整性错误、权限失控、隐私矛盾；
- C：过度设计 + 细节规则缺失。

### 6.3 差异原因

1. **交互方式决定信息密度**：访谈是逐层剥洋葱，能拿到隐式知识；一次性陈述只能拿到显性功能；多 Agent 制造了“多轮”，但没有真实追问，仍需人工裁决。
2. **模型有“补全冲动”**：输入缺少规则时，模型会默认一个“合理”的做法。B 的“退出余额清零”就是简化流程导致的错误补全。
3. **多 Agent 能查矛盾，但不能控范围**：评审代理能发现“退款前置条件与正文不符”，但它不会主动说“校园卡这个项目不该做”。
4. **金额与权限是高风险领域**：金额守恒、权限最小化、操作可追溯，这些隐含不变量一旦写错，后面全错。
5. **学生的输入质量决定上限**：A 的回答包含大量真实约束（24 小时、7 天、50 人、180 天）；B 的草稿是愿望清单；C 把裁决权交给 Agent，自己只在最后做取舍。

### 6.4 成本—收益与推荐流程

- B 到 A：多投入 35 分钟，完整度 +30 个百分点，返工大幅下降；
- A 到 C：完整度 +7 个百分点，但引入 4 条过度设计；
- 最优组合不是单独使用某一种，而是：**多 Agent 查漏 → 人做访谈澄清 → 人定范围 → AI 成稿 → 人逐条验证**。

完整对比报告：[06-对比分析.md](https://github.com/Zhyuan0001/campus-expense-tracker/blob/master/docs/requirements-v4.0/06-%E5%AF%B9%E6%AF%94%E5%88%86%E6%9E%90.md)。

### 7.2 关键业务规则

**金额守恒**

- 所有金额以整数“分”存储和计算；
- 单笔支出金额 >0 且 ≤1,000,000 元；
- 每人分摊金额 >0，Σ分摊 = 支出金额；
- 均分余数按“付款人优先，其余按参与顺序”逐分分配；
- 成员净额合计必须为 0，否则拒绝结算。

**权限边界**

| 操作 | 普通成员 | 管理员 Admin | 创建者 Owner |
|---|---|---|---|
| 查看流水与统计 | 允许 | 允许 | 允许 |
| 新增共同支出 | 允许 | 允许 | 允许 |
| 编辑自己 24 小时内的支出 | 允许 | 允许 | 允许 |
| 编辑他人支出 | 不允许 | 允许（留痕） | 允许（留痕） |
| 删除支出 | 仅自己 24 小时内 | 允许 | 允许 |
| 发起退款 | 仅自己创建的支出 | 允许 | 允许 |
| 生成/撤销邀请 | 不可生成，可转发 | 允许 | 允许 |
| 移除普通成员 | 不允许 | 允许 | 允许 |
| 移除管理员 | 不允许 | 不允许 | 允许 |
| 设置/撤销管理员 | 不允许 | 不允许 | 允许 |
| 转让创建者 | 不允许 | 不允许 | 允许 |
| 设置共享预算 | 不允许 | 允许 | 允许 |
| 导出全账本 | 不允许 | 允许 | 允许 |
| 查看审计日志 | 不允许 | 允许 | 允许 |
| 归档/删除账本 | 不允许 | 不允许 | 允许 |

**成员退出**

- 余额为 0 才能主动退出；
- 余额不为 0 时，只能先结算，或由创建者强制移出并承接余额；
- 退出/被移出后立即失去访问权，历史记录保留；
- 创建者不能直接退出，必须先转让或删除账本。

**退款与结算**

- 只做整单退款，按原分摊比例冲销；
- 已结算支出不可退款，退款后原支出锁定；
- 结算采用贪心方案，转账笔数 ≤ 成员数 − 1，不保证全局最优；
- 付款方标记已转账，收款方确认到账；支持部分结清，争议可拒绝回退；
- 已确认的结清记录不因新增支出而撤销，新增支出只影响未结清部分。

**邀请与审计**

- 6 位邀请码，7 天有效，可撤销，可多人使用；
- 账本上限 50 人；邀请码尝试 5 次/10 分钟，超过锁定 10 分钟；
- 审计日志保留 180 天，到期归档，仅 Owner 可申请导出后清理。

**并发与隐私**

- 支出和结算记录使用版本号，后保存方收到冲突提示；
- 客户端提交使用幂等键，避免网络重试产生重复记录；
- 非成员不可查看账本；个人账本互不可见；联系方式默认隐藏；
- 不接第三方统计；支持导出和删除个人数据。

| 只说“帮我审查补全” | 明确“未确认的内容必须单独标注，不得写成确定需求” |
| 没有限制范围 | 在提示词里列出范围外清单，要求模型不得新增 |
| 没有要求来源 | 每条需求标注“来自哪一轮回答/哪个角色” |
| 没有金额规则 | 明确金额以分计算，给出余数归属规则 |
| 没有权限矩阵 | 先输出角色权限矩阵，再写功能需求 |
| 没有评审环节 | 增加独立评审 Agent，只挑错不重写 |
| 没有优先级 | 要求 P0/P1/P2，并说明 P2 默认不做 |

---

## 九、反思：AI 是需求实习生，不是决策者

这次实验最大的收获，不是“AI 能写出一份像样的需求文档”，而是看清了它的边界：

- 让 AI 做结构化、补场景、写用例，效率很高；
- 让 AI 做范围控制、业务规则裁决、优先级排序，风险很高；
- 最可靠的流程是：**多 Agent 查漏 → 人做访谈澄清 → 人定范围 → AI 成稿 → 人逐条验证**；
- 对金额、权限、状态机这类高风险需求，必须用“守恒规则 + 权限矩阵 + 验收用例”三件套兜底。

需求工程里最难的从来不是“写文档”，而是“决定什么不做”。这一点，AI 目前还替不了人。
