## 3. 修改前后对照

### 3.1 成员退出

**AI 原稿（B）**：

> 成员可随时退出账本，退出后其未结清余额自动清零。

**问题**：余额不会凭空消失，清零等于把债务转嫁给其他成员，直接违反“Σ净额 = 0”。

**最终版（FR-07）**：

> 成员余额为 0 时可主动退出；余额不为 0 时提示先结算；Owner 不能直接退出，需先转让或删除账本；Owner 强制移出成员时，余额由 Owner 承接并留痕。

### 3.2 删除权限

**AI 原稿（B）**：

> 所有成员可编辑和删除任意记录；删除后不可恢复。

**问题**：普通成员可以删除别人的记录，且无法追溯，和“数据安全”目标冲突。

**最终版（FR-10）**：

> 记录创建者 24 小时内可编辑/删除自己的记录；Owner/Admin 可编辑任意记录；删除为软删除，30 天内可恢复；已结算、已退款、归档账本不可改删；全程写审计日志。

### 3.3 结算算法

**AI 原稿（C）**：

> 用最少的转账笔数完成全员结清（全局最优）。

**问题**：这是组合优化问题，课程项目没有足够时间实现和验证；用户对“少一两笔”并不敏感。

**最终版（FR-13）**：

> 采用贪心方案：净欠款最多者向净应收最多者转账，金额取两者绝对值较小者；转账笔数 ≤ 成员数 − 1；界面明确说明“不保证全局最优”。

### 3.4 邀请机制

**AI 原稿（B）**：

> 邀请链接永久有效，可多人使用，人数不设上限。

**问题**：链接一旦泄露无法收回，账本可能被陌生人加入。

**最终版（FR-04）**：

> 6 位邀请码 + 链接，7 天有效，可撤销，可多人使用；账本上限 50 人；同一账号 10 分钟内最多尝试 5 次，超过锁定 10 分钟；仅 Owner/Admin 可生成和撤销。

## 4. AI 做得好的地方

| 能力 | 表现 | 例子 |
|---|---|---|
| 结构化 | 能把口语化草稿整理成功能/非功能/约束 | B 的文档结构被最终版采用 |
| 场景补全 | 能想到审计、并发、软删除、部分结清 | A 的 24 小时编辑窗口、180 天日志 |
| 多视角 | 能模拟不同角色提出差异化诉求 | C 的宿舍长/普通成员/社团财务 |
| 交叉检查 | 评审代理能发现前置条件与正文矛盾 | C 发现退款规则矛盾、Admin 边界缺失 |
| 用例编写 | 能按模板生成参与者、前置/后置条件 | A/C 的用例表直接可用 |

## 5. AI 不能替代人的地方

1. **范围控制**：AI 倾向于“把能想到的都写上”，必须由人做减法和优先级排序；
2. **业务不变量**：金额守恒、权限最小化、操作可追溯，这些规则一旦写错，后面全错；
3. **真实约束**：7 天、50 人、24 小时、180 天这些数字来自真实业务判断，AI 不会自己知道；
4. **责任归属**：需求确认需要利益相关方签字，AI 不能替代；
5. **可测试性**：AI 容易写“快速、合理、尽量”，必须改成可验证的阈值。

## 6. 提示词改进清单

| 原提示词问题 | 改进 |
|---|---|
| 只说“帮我审查补全” | 明确写出“未确认的内容必须单独标注，不得写成确定需求” |
| 没有限制范围 | 在提示词中列出范围外清单，要求模型不得新增 |
| 没有要求来源 | 要求每条需求标注“来自哪一轮回答/哪个角色” |
| 没有金额规则 | 明确“金额以分计算，给出余数归属规则” |
| 没有权限矩阵 | 要求先输出角色权限矩阵，再写功能需求 |
| 没有评审环节 | 增加独立评审 Agent，只挑错不重写 |
| 没有优先级 | 要求 P0/P1/P2，并说明 P2 默认不做 |

## 7. 结论

这次任务最大的收获不是“AI 能写需求文档”，而是看清了它的边界：

- **让 AI 做结构化和查漏，效率很高**；
- **让 AI 做范围控制和业务规则裁决，风险很高**；
- 最可靠的流程是“多 Agent 查漏 → 人做访谈澄清 → 人定范围 → AI 成稿 → 人逐条验证”；
- 对金额、权限、状态机这类高风险需求，必须用“守恒规则 + 权限矩阵 + 验收用例”三件套兜底。
